一、协议总览

1.1 通信层次

层协议用途
消息总线WebSocket :3002主服务器 ↔ 所有客户端 (display / RDC / RTC / Editor / register / query / 等)
Web 文件服务HTTP :8080主服务器提供 display.html / control.html / race_control.html / query.html 等
硬件计时TCP 5555 / UDP 5002 / 串口 (RS232)计时主控 (主服务器或 RTC) ↔ 硬件计时器
v2026.06.19 实测: 硬件 TCP 链路下硬件开始送时间帧后 PC 端 HTML 客户端污染 (全 0 / 闪烁 / 调不到数据). 大型比赛优先 RS232, TCP 链路问题待固件层后续修复.

JSON 文本, 顶层字段:

{

所有时间字段统一格式: 分:秒.毫秒 (例 1:23.45) 或纯秒 23.45。

五、RTC 转发链 (RTC_FORWARD)

5.1 设计目的

RTC.exe 直连硬件, 但不开自己的 WebSocket Server (端口 3002 冲突), 通过主服务器中转大屏数据。

5.2 消息格式

{
  "type": "RTC_FORWARD",
  "payload": { ... }   // 完整的 SHOW_LIVE_RACE / SHOW_HEAT_RESULT 等消息
}

5.3 主服务器 RTC_FORWARD 处理

主服务器收到 RTC_FORWARD 时:

  1. 缓存 payload 到 _lastRtcSnapshot
  2. 把 payload 原样广播给所有 display 客户端 (BroadcastJsonToClients)

5.4 新连接 display 的初始化

新连接的 display 第一时间收 _lastRtcSnapshot, 立即恢复显示 (不等下一帧 RTC 推送)。

5.5 RTC 端节流

RTC Broadcast 100ms 节流, 多次事件合并一次推主服务器。

六、编排同步 (EDITOR_*)

6.1 整包推送

消息方向用途
EDITOR_PACKAGE主服务器 → 编排端整包 (CompetitionPackage JSON), 含项目/运动员/赛程/纪录等
EDITOR_PUSH_PACKAGE编排端 → 主服务器编排端改完回推

6.2 RTC 1.5s 去抖

主服务器改赛程 → RTC 端 EditorSyncClient 收到后启动 1.5s 定时器, 期间多次推送合并, 到期才应用最新一份。 避免编排端连续编辑导致 RTC 频繁全量重建。

6.3 编排端身份

ScheduleEditor / RegistrationTool / register.html 连主服务器时发 EDITOR_IDENTITY, 主服务器加入 _editorClients 集合, 每次 AutoSaveData 后自动推 EDITOR_PACKAGE。

11.3 颁奖 / 总排名回放字段 v2026.06.21 新增

PC 端用户从 "颁奖" / "总排名" 弹窗选定项目后, GetStatusData 投影附加:

  • awardSelection / awardRanking: SHOW_AWARDS 模式下, display.html 优先用此项目 (= 全项目总排名前 3) 渲染领奖台
  • rankingSelection / rankingRanking: SHOW_EVENT_RANKING 模式下, display.html 强制单表分页, 10 行 1 页轮播
  • 切到其他大屏模式 → 服务器自动清这两组字段
  • display.html 检测 selection 为 null 时退回 currentXxx + eventRanking (兼容远端直接命令)

11.4 排名字段 (eventRanking / awardRanking / rankingRanking)

统一结构, 每元素:

{
  "rank": 1,           // 名次 (0 = DSQ/DNS/DNF/无成绩)
  "heat": 1,
  "lane": 4,
  "bibNumber": "001",
  "name": "魏延北",
  "country": "兰州文理",
  "entryTime": "0:28.55",
  "finalTime": "0:27.85",
  "timingSource": "TP",
  "status": "",         // 空 / DSQ / DNS / DNF
  "resultStatus": "",
  "recordNote": "WR",   // 破/平纪录标识
  "qualifiedToNext": false
}

排序规则 (v2026.06.22):

  1. 有成绩运动员按 FinalTime 升序 (并列名次 1-2-2-4)
  2. 末尾追加 DSQ/DNS/DNF 等 (rank=0), 按 DSQ → DNF → DNS → 其他 排序 (用户要求)
  3. TRI 试游不进总排名 (= 仅展示, 排除)

11.5 RUNNING_TIME_UPDATE

硬件 100ms 节拍, 轻量级滚动时间帧:

{
  "type": "RUNNING_TIME_UPDATE",
  "data": {
    "runningTime": "35.42",
    "clockPaused": false
  }
}

客户端注意: 必须按 msg.type 白名单分发处理, 不能 if (msg.data) { data = msg.data } 全吞, 否则 RUNNING_TIME_UPDATE 会覆盖整个 data, 导致 schedule/allSwimmers 丢失 (整页闪烁)。

11.6 STAGE_COMPLETE / PROMOTION_DONE

十二、硬件计时器协议 v2026.06.22 仰泳重构

12.1 物理层

方式参数

12.5 硬件 0x16 D3 子类型详解

D3 值含义PC 端 cmdType触发场景
0真触板 (TP 松开 1→0 边沿)Touchpad正常分段触板 / 终点
1盲表代触ManualTouchpad硬件用盲表中位代替坏 TP
3仰泳出发松开 TP v2026.06.22 位置修正BackstrokeRelease仰泳 + Ready_timer_bit=1 + GunFired_PostOpenDoneBit=0 + TP 松开
4手动 TP 键ManualTouchpad裁判按手动按键代触

12.6 仰泳协议彻底重构 v2026.06.22 重大改动

问题描述

固件 v2026.06.21 及之前: 100m+ 仰泳运动员到终点 (出发端=终点端) 没成绩。

根因 (固件 vs PC 协议错位)

事件PC 协议期望固件 v2026.06.21 实际v2026.06.22 修正
TP 按下 (KeyState 0→1, 预备脚踩)不发任何帧发 D3=3 BackstrokeRelease ❌ 位置错✓ if(0) 禁用
TP 松开 (KeyState 1→0, 出发蹬出)发 D3=3 + 不减圈发 D3=0 Touchpad + Display_Laps_Place_Direct (减 1 圈) ❌✓ 仰泳分支发 D3=3 + 不减圈, 其他分支照旧

固件改动位置 (swimplay.c)

行号改动
4724左端 TP 松开减圈守卫: Display_Laps_Place_Direct(i,0) 前加 !(BackstrokeBit==1 && Ready_timer_bit==1 && GunFired_PostOpenDoneBit==0)
4726-4738左端 TP 松开协议对齐: 加 if 仰泳分支发 D3=3, else 分支保留原 D3=0
4769左端 TP 按下: if(0) {...} 禁用原 BackstrokeRelease 块
4837右端 TP 松开减圈守卫 (对称)
4850-4862右端 TP 松开协议对齐 (对称)
4894右端 TP 按下禁用 (对称)

反应时"覆盖迭代"

每次 TP 松开都覆盖 BackstrokeRelease_PreStart_*[i][0/1] + BackstrokeRelease_Valid[i][0/1] = 1, 取最新一次蹬出时刻 (= 与 PC 端 ReactionTime 覆盖行为对齐)。

PC 端守卫 (defense-in-depth)

PC 端 case "Touchpad" 入口仍保留 "仰泳 + 出发端 + CurrentLap=0 + 非 MB 代触 → 丢弃" 守卫作冗余防御, 固件回滚或老固件时兜底。
