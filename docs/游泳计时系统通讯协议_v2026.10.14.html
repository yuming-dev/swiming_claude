一、协议总览

1.1 通信层次

层协议用途
消息总线WebSocket :3002主服务器 ↔ 所有客户端 (display / RDC / RTC / Editor / register / query / 等)
Web 文件服务HTTP :8080主服务器提供 Web/ 目录下全部静态文件 (display.html / control.html / race_control.html / query.html 等，见 §13)
竞赛数据服务 本版新增小节WebSocket :3002 内的 MeetRpc 请求/响应主服务器独占 meet.db，其它机器(ScheduleEditor 等)通过 RPC 读写，而不是各自开库。详见 §1.4
硬件计时TCP 5555 / UDP 5002 / 串口 (RS232)计时主控 (主服务器或 RTC) ↔ 硬件计时器
v2026.06.19 实测: 硬件 TCP 链路下硬件开始送时间帧后 PC 端 HTML 客户端污染 (全 0 / 闪烁 / 调不到数据). 大型比赛优先 RS232, TCP 链路问题待固件层后续修复. (本版未见该问题修复记录，结论维持不变。)

1.2 WebSocket 消息格式

JSON 文本, 顶层字段:

{
  "type": "消息类型大写下划线",
  "data": { ... }  // 可选, 消息体
}

所有时间字段统一格式: 分:秒.毫秒 (例 1:23.45) 或纯秒 23.45。

1.4 竞赛数据服务 (MeetRpc) 本版新增小节

主服务器是 meet.db(竞赛库，成绩/名次/审计日志)的唯一持有者；其它机器不再各自打开这份数据库文件， 而是通过 WebSocket 内的一套 RPC 请求/响应（SwimmingScoreboard.Db.MeetRpc.RequestType，由 HandleMeetRpc 处理） 向主服务器请求读/写。

本节未展开：这是本版审查中发现的一个结构性较大的新增子系统，但具体消息形状(RequestType 枚举值、请求/响应字段)本轮未逐一核实， 留作后续专项补充。日常集成如需用到，建议直接查 Db/MeetRpc.cs(或同名命名空间下的协议定义文件)与 MainWindow.xaml.cs 里的 HandleMeetRpc 实现。

五、RTC 转发链 (RTC_FORWARD)

5.1 设计目的

RTC.exe 直连硬件, 但不开自己的 WebSocket Server (端口 3002 冲突), 通过主服务器中转大屏数据。

5.2 消息格式

{
  "type": "RTC_FORWARD",
  "payload": { ... }   // 完整的 SHOW_LIVE_RACE / SHOW_HEAT_RESULT 等消息
}

5.3 主服务器 RTC_FORWARD 处理

主服务器收到 RTC_FORWARD 时:

  1. 缓存 payload 到 _lastRtcSnapshot
  2. 把 payload 原样广播给所有 display 客户端 (BroadcastJsonToClients)

5.4 新连接 display 的初始化

新连接的 display 第一时间收 _lastRtcSnapshot, 立即恢复显示 (不等下一帧 RTC 推送)。

5.5 RTC 端节流

RTC Broadcast 100ms 节流, 多次事件合并一次推主服务器。

本节本版未发现明确变化（未找到 payload 上出现按 to 字段区分收件人范围的新路由逻辑），维持 v2026.06.22 时点描述。 若后续排查广播范围相关问题，建议直接在 BroadcastImmediate()/BroadcastJsonToClients 源码核实一次，不要只信这份文档。

六、编排同步 (EDITOR_*)

6.1 整包推送（原有机制，保留）

消息方向用途
EDITOR_PACKAGE主服务器 → 编排端整包 (CompetitionPackage JSON), 含项目/运动员/赛程/纪录等
EDITOR_PUSH_PACKAGE编排端 → 主服务器编排端改完回推
EDITOR_PUSH_REJECTED 本版新增主服务器 → 编排端{reason}。整包回推若被 IsPackageApplyBlocked 判定命中(存在正在比/成绩未确认的组)，主服务器不再静默丢弃，而是明确回这条拒绝消息——用户手册 9.2 节"被拒时编排端会明确告诉你原因"背后的协议落点

RTC 端 1.5s 去抖、编排端身份声明两段内容未变：主服务器改赛程 → RTC 端 EditorSyncClient 收到后启动 1.5s 定时器， 期间多次推送合并，到期才应用最新一份；ScheduleEditor / RegistrationTool / register.html 连主服务器时发 EDITOR_IDENTITY，主服务器加入 _editorClients 集合，每次 AutoSaveData 后自动推 EDITOR_PACKAGE。

6.2 增量补丁 (EDITOR_PATCH) 本版重点新增

这是本版协议层面最大的新增机制，对应用户手册 4.5 节"比赛中可以改别的项目"和 9.1 节"两种同步方式"。 并组、道次/分组调整、临场微调、晋级处理、纪录维护这几类最常用的临场操作，不再走 6.1 的整包推送， 而是只把"这一次操作"本身发给主服务器，秒级生效，且不会跟正在计时的那一组冲突。

请求

{
  "type": "EDITOR_PATCH",
  "op": "<操作名>",
  "corrId": "...",      // 关联 ID，用于匹配下面的 ACK
  ... // 按 op 不同，携带各自的字段
}

已确认的 op 取值

op用途
Assign分组/道次指派类调整（上移/下移/交换泳道/增加到本组/移出本组等落到这一类操作）
MergeHeats并组/取消组。字段比较完整，单独列出：{ageGroup, gender, eventName, stage, reason, clientName, srcHeat, dstHeat}——dstHeat 省略或特殊值表示"仅取消，不并入"
Unlock解锁本组成绩（编排端入口；计时站侧走 §4 的 TIMING_CMD UNLOCK_HEAT_RESULT，两条路最终效果一致）
CheckIn检录状态变更
RelayEdit / RelayDelete接力队信息编辑 / 删除
SwimmerEdit / SwimmerDelete运动员信息编辑 / 删除
SwimmerRowsAdd / SwimmerRowsUpsert批量新增 / 新增或更新运动员行（CSV 导入等场景）
Records纪录维护。特殊：此 op 成功后不触发下方的 meet.db 防抖重建（纪录表不进 heat 相关的同步路径）
ListSet整表替换类操作（具体对应项目/组别/性别/赛次四张表中的哪一张，取决于附带字段，未逐一核实）

响应

{
  "type": "EDITOR_PATCH_ACK",
  "corrId": "...",
  "ok": true,
  "reason": "..."   // ok=false 时携带拒绝原因
}

成功后的连锁动作

  1. 把这条 EDITOR_PATCH 原样转发给其它所有已连接的编排端 socket（不重新处理，纯转发，让其它编排端界面跟着刷新）
  2. 除 op == "Records" 外，触发一次 0.5 秒防抖的 meet.db 增量重建（ScheduleMeetDbSyncFromPatch / MeetDbSyncDebounceTick）——这个防抖时长本版从 2 秒缩短为 0.5 秒

相关：HEAT_CONFIRMED_ACK 本版新增

另有一条独立的 HEAT_CONFIRMED_ACK 确认消息，在两处"确认本组成绩"相关调用点发出；具体字段形状本轮未核实， 推测与"某一组成绩确认后，通知相关编排端刷新"有关，对接前建议抓包确认。

拒绝判定：无论是整包推送(6.1)还是增量补丁(6.2)，命中"该组正在计时/已就位/已完赛/已有未确认成绩"任一条件都会被拒绝—— 这跟用户手册 4.5 节"按组上锁，不是按『比赛中』一刀切"完全对应，不要在协议层面假设"没有比赛就等于能改任何东西"， 具体判定逻辑仍以 IsHeatLocked/IsPackageApplyBlocked 一类的服务端函数为准。

十一、大屏推送消息 (SHOW_*)

11.0 大屏推送帧瘦身机制 (staticOmitted) 本版重点新增，2026-08-25

随着状态包字段越来越多，每 100ms 心跳都把 allSwimmers/schedule/eventList 这类"重/静态"字段 整包重发的成本越来越高。本版引入 staticOmitted 机制：

{
  "type": "SHOW_LIVE_RACE",
  "data": {
    "staticOmitted": ["allSwimmers", "schedule", "eventList", ...],  // 本帧省略了哪些字段
    // 省略的字段不会出现在 data 里；客户端应保留上一次收到的旧值，不能当成"清空"处理
    ...
  }
}

默认省略列表（非"全量帧"/非 keepStatic 请求时）：allSwimmers, allRelayTeams, schedule, teamScores, ageGroups, ageGroupsDetail, eventList, genderList, stageList, eventRanking, eventRankingSplit, applicableRecords, laneEventLogs, laneDevices。

客户端必须读 staticOmitted 后再决定是否清空/覆盖对应字段。 这是对 v2026.06.22 旧版 11.5 节 "不能 if (msg.data) data = msg.data 全吞"那条告诫的进一步延伸——不仅 RUNNING_TIME_UPDATE 这类独立消息类型要白名单处理， 连 SHOW_LIVE_RACE 本身的常规帧现在也可能是"精简帧"，贸然把 data 整体覆盖旧状态会导致运动员名单、赛程树等大面积丢失。

十二、硬件计时器协议 本版重新核对全表

本版勘误说明：v2026.06.22 版的 12.3/12.4 表格存在两处实质性错误，本版对照 TimingBridge.cs 源码逐条核实后改正： (1) 0x66 被同时标成"硬件→PC 的 EventBackup 帧"和"PC→硬件的 EventBackupQuery"——实际上 0x66 只是 PC→硬件 的查询命令（Query_BackupLog_Command），硬件返回的备份事件数据帧是 0x67，两个方向不是同一个字节； (2) 0x42 被标注为"StartPosition"，但源码里 0x42 实际是通用的 SetCommand（子码 0x01-0x0A）， 不是专门的起点位置命令。下表已按源码改正，不确定具体子码含义的地方会明确标注"未核实"，不再凭猜测填写。

12.1 物理层

方式参数
TCP硬件 5555, PC 主动连
UDP硬件→PC: 5002, 双向广播
串口 (RS232)115200 8N1
v2026.06.19 实测警告: TCP 链路下硬件开始送时间帧后 PC 端 HTML 客户端数据污染. 切 RS232 即恢复. 大型比赛优先 RS232 链路. (本版未见修复记录，结论维持不变。)

12.2 帧格式

F1 53 [CMD] [D3] [D4] [D5] [D6] [D7] [D8] [D9] [D10] F4
↑头  ↑     ↑cmd ↑D3 ↑D4=泳道号  …各 cmd 自己定义…    ↑尾

全部 12 字节：D0=0xF1(SOH)，D1=0x53('S')，D2=命令字节，D11=0xF4(EOT)。 命令字节在代码中直接按原始值使用，不存在"wire 字节再减 0x10"的通用换算——这是本版勘误的重点之一， 唯一例外是 0x69 Set_StrokeType 命令的firmware 内部历史渊源（见 12.5 脚注），不是普适规则。

12.6 命令字节历史沿革备注 本版新增

  • 0x3B 的两次生命：这个字节早期曾私下挪用给 Set_ForceAllOpen，后来改为官方的 0x4C； 本版(2026-10-14)起 0x3B 重新启用，正式含义是 Set_Language（见 12.4）。旧固件若收到这帧会落入 default 分支忽略，不报错也不会真的切换硬件界面语言，需要升级到对应固件版本才会生效。
  • 0x46 → 0x69 的迁移：泳姿类型设置命令最初用 0x46，但该字节已被 Set_TPSBMB_State（设备好坏+启用位）占用， 且硬件内部按键命令分发表用"wire 字节 − 0x10"作索引（Receive_Button_Command_Value = wire-0x10），两者在这张内部表里也撞了， 导致 case 分支永远匹配不到。修正为使用 0x69（内部对应 0x59 = 0x69-0x10，未被占用）后解决。 这条"wire − 0x10"换算只是这一处按键命令分发表的内部实现细节，不是整个协议的通用规则（呼应 12.2 的勘误说明）。
  • 与 0x60/0x4C/0x47 三条"泳道开关类"命令的语义区分：
    命令作用范围效果
    0x47全部或单道整体启用/禁用 TP/SB/MB（不动道次按钮显示）
    0x60仅单道同时切换 TP/SB/MB 启用 + 道次按钮显示状态
    0x4C全部或单道设备状态机覆盖（接受所有信号 vs 按状态过滤）
