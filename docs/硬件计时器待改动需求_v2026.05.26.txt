┌──────────────────────────────────────────────────────────────┐
│ 1. ★★★【必修】0x20 Timer_Reset 不应清掉 0x41 d8 配置位       │
│      (FinalPlace + StartPlace50M + LaneDirect)                │
└──────────────────────────────────────────────────────────────┘

  现象（用户报告 2026-05-26）
  ────
  操作员在 PC「参数设置」中把"终点位置"从左端改为右端，
  →「准备就绪」→「M.发令」。
    • 发令、反应时、所有状态指示灯都正常 ✓
    • 倒计时到 0 后触板/盲表打开端 PC 显示也正确 ✓
    • 运动员完赛触板（在右端）后 → **PC 端没有任何显示**
      就像 PC 没收到数据一样。

  PC 端追踪后确认：
    • 硬件**确实**回报了触板数据（serial log 看得到 F1 53 16 ... F4）
    • 但帧里 D4 字段 < 10（硬件标记为"finish end"），
      而 PC 此时 FinishPosition=right，按协议 PC 把 D4<10 映射成
      side="right" → 查 RightTouchpadStatus → ProcessTouchpadHit ✓

      ↑ 这条链路本应工作，但实际不行。原因是硬件这次发的
      "finish end" 实际指的是左端，因为硬件**自己**的 FinalPlace
      状态早被 0x20 清成默认 0（左）了。

  根因推断
  ────
  PC 在「准备就绪 / 计时复位 / WebSocket TIMER_RESET」三处都会发
  0x20 给硬件。协议文档早已注明 0x20 会清缺道位图，PC 也补发 0x43。
  但**实测发现硬件 0x20 处理还会顺带清掉 0x41 d8 里的三个配置位**：
      d8 bit 0 = FinalPlace  (终点端 0=左/1=右)
      d8 bit 1 = StartPlace50M (50 米发令端不同于终点)
      d8 bit 4 = LaneDirect  (道次顺序 0=正序/1=逆序)
  → 复位后这三个位全回到 0。
  → FinishPosition=right 的用户复位一次就掉回 left（硬件视角），
    完赛端被错分类为 "finish end" 实际指的是错的一边，
    PC 这边把它再映射成"完赛侧"看到的当然是 Closed → 静默丢弃。

  PC 侧补救（已做 — commit 计划随本提交）
  ────
  MainWindow.xaml.cs 4 处发完 0x20 后立刻追发：
      SendSetMatchEventToHardware()    // 0x43（之前就有）
      SendTimingSettingsToHardware()   // 0x41 + 0x44 + 0x45 ← 新加
      SendStartPositionToHardware()    // 0x10 0x42         ← 新加
  覆盖 EnterReadyStateInternal / Restart_Click(主分支+无当前组分支)
  / WebSocket RESTART 这 4 处。

  期望的硬件行为
  ────
  Timer_Reset_Command 处理里应该**只清掉计时相关状态**（CurrentTime、
  LapCount、缺道位图等），不要碰下面这些"用户配置"位：
      d8.FinalPlace
      d8.StartPlace50M
      d8.LaneDirect
      其它由 0x41 / 0x44 / 0x45 / 0x10 0x42 配置的字段
  这样 PC 一次配置后中途任意复位都不会丢失参数，节省 5+ 条同步帧。

  PC 侧补救的代码可以保留作防御（"双保险"），不冲突。

│ 2.【信息 / 已纠正】0x41 d8 bit 0 的协议命名                    │
└──────────────────────────────────────────────────────────────┘

  情况说明
  ────
  通讯协议 v2026.05 (2026-05-20 版) 文档把 d8 bit 0 命名为 StartPlace
  (起点端)。实际硬件 swimplay.c 实现里这一位一直是 FinalPlace
  (终点端)。

  PC 端 b45274e commit 已修正：发送 FinishPosition 而非 StartPosition。
  通讯协议 v2026.05.26 文档已纠正命名。
  硬件端**不需要任何改动**。

  说明这一点是因为前一份 v2026.05.26 调查请求文档（已作废）误以为
  根因在这里。实际这只是 PC 端协议字段误读，不影响 50m 之外的比赛
  （100m+ 因 StartPosition == FinishPosition 所以 PC 误读也能给出
  正确的 bit 值，没暴露问题）。


┌──────────────────────────────────────────────────────────────┐
│ 3. ★★【建议】其它 0x20 副作用排查                             │
└──────────────────────────────────────────────────────────────┘

  既然发现了 0x20 顺手清 0x41 d8 这种"非计时状态"，建议硬件工程师
  完整审计 Timer_Reset_Command 处理段，确认还有没有别的状态被无意
  清掉。已知已修复的：
    • 0x65 Set_RefreshDisplay 会清 race distance — 见 2026-05-25
      待改动需求文档 §1
    • 0x20 Timer_Reset 清缺道位图 — 协议早有记录
    • 0x20 Timer_Reset 清 0x41 d8 配置位 — 本文档 §1

  建议方向：把"计时状态"和"用户配置状态"分成两个变量域，复位类命令
  只清前者；配置类命令（0x41/0x43/0x44/0x45/0x10 0x42/0x3A 等）写
  后者；二者之间没有覆盖关系。
