## ② meet.db 依赖 —— 通道已通，但计时端没配

### 现在的分工（`Db/MeetDbBridge.cs`，已实现）

| 操作 | 走哪 | 说明 |
|---|---|---|
| `UpdateLane` / `UpdateSplit` / `SetRaceState` | **本机** `current_heat.db` | 比赛中每一次触板都写这里，不过网 |
| `GetSchedule` / `OpenHeat`（取名单） | 远端 `MEET_RPC` | 只在**选组**时调一次 |
| `CommitHeat`（确认成绩） | 远端 `CommitHeatFrom(_local.GetLiveHeat())` | 把本机成绩**整组带过去**再入库 |
| 破纪录 | 随 `CommitHeat` 返回 `RecordBreak` 列表 | 服务端判定，不用单独接 |
| 团体总分 | `CalculateTeamScores()`（`:12781`） | 目前在**主服务器**算 |

`RemoteMeetService` 对"当前组库"类操作直接抛异常（`:157 NotOverWire`），
从设计上就堵死了"比赛中过网写数据"这条错路 —— 这是对的，别去改它。

**这条链路 2026-08-27 实测过：比赛中 `GetSchedule` 可用，返回 45 行带 RoundId。**

### ❌ 缺口：计时端根本没进远端模式

`MeetDbBridge` 自己读配置（`:70-99`）：

```
命令行   --meet-server 192.168.1.10[:3002]
配置文件 <程序目录>\meet_service.json  { "Host": "..." }
```

**但安装包的 `RemoteTimingControl\` 目录里没有 `meet_service.json`**
（只有 `RemoteTimingServer.txt`，那是另一回事）。

后果：计时端会**退回本地模式**，自己开一个 `meet.db`。比赛中不会立刻出错
（当前组走本机库），但**确认成绩会写进计时端自己的库**，主服务器那边什么都没有。
这是转移方案里**最危险的一个洞**，必须先堵。

**要做的**：安装时在计时端目录写 `meet_service.json`，Host 指向主服务器；
或者在计时端界面上把已有的「主服务器 IP」输入框跟它打通（现在那个框只管
EditorSync，不管 MeetDbBridge，**两套配置各走各的**——这本身也该合并）。

### 还需要逐个确认的（我没查）

## ③ 掉线接管 —— 现在没有，建议这样定

**现状**：主服务器的「比赛控制」页可以用 `--role server` 移除
（`ApplyMachineRoleToUi()` → `tc.Items.Remove(RaceControlTab)`，`:404`），
计时命令也会被拒并回执 `TIMING_CMD_REJECTED`。**但这个开关目前没人用**，
现场跑的是 `standalone`。

**问题**：一旦主服务器真的把比赛控制去掉，计时端死机 / 网线断了，就没有第二条路。

**建议：不做自动接管，做"手工降级"。**

理由：自动接管要处理"两台都在控制"的脑裂，比赛现场出这个问题比停几分钟更糟。

具体做法：

1. 主服务器**保留**比赛控制页的代码和界面，用 `--role server` **默认隐藏**
2. 加一个隐蔽的「应急接管」入口（比如设置页里，需要二次确认）
3. 接管时先检查计时端是否真的离线（主服务器知道 RTC 有没有连着）
4. 接管后在界面上挂持续可见的警示条，提醒赛后要恢复

这样**代码一行不用删**，跟你定的"不删代码、只用运行时开关"是一致的。

### 第 3 步 —— 已查清（2026-08-28）

| 功能 | 落在哪台机器 | 数据来源 | 转移后怎么办 |
|---|---|---|---|
| **打印成绩** | **点按钮的那台** | 内存 `_swimmers` 当前组 | 计时端能打。要就近放小票机/打印机 |
| **公布项目总排名（存盘）** | **点按钮的那台的硬盘** | 内存 | ⚠️ **要决策**，见下 |
| **团体总分** | 内存现算，不落地 | `_swimmers` 全部成绩 | 已修：回推后自动重算 |

细节：

- **打印成绩** → `GenerateAndOpenDocument("分组成绩", ...)`：在
  `<程序目录>\Documents\` 下生成 html 再打开。**纯本机行为**，计时端上点就在计时端出。
  数据来自内存当前组，计时端本来就有 —— 能正常用。

- **公布项目总排名（存盘）** → 写 txt 到 `GetAutoSaveTxtDir()`：
  优先 `_autoSaveTxtPath`（界面可配），没配就是 `<程序目录>\Documents\成绩txt`。
  **写的是本机硬盘**。转移之后，操作员在计时端点这个按钮，txt 就落在**计时端**上，
  而不是主服务器。

  **要你决策**（三选一）：
  1. 把计时端的存盘路径配成**主服务器的共享目录**（`\\主服务器\成绩txt`）—— 改配置即可，最省事
  2. 存盘也走 RPC，由主服务器写 —— 要加接口，但赛后取文件只认一台机器
  3. 就让它落在计时端，赛后手工拷 —— 不推荐，容易忘

  **已定：选 1** —— 把计时端的存盘路径配成主服务器共享目录。不动代码，
  运维上也说得通（成绩文件本来就该集中放）。

  配法：计时端「设置」里改成绩存盘路径为 `\\主服务器名或IP\共享名`，
  主服务器那边把该目录共享出来并给计时端写权限。

  **防呆**：已加提示 —— 计时端点「公布项目总排名(存盘)」时，如果路径还是本机路径
  （不是 `\\` 开头的共享路径），日志会写一行
  「注意: 成绩 txt 存在【本机(计时端)】… 建议改成主服务器共享目录」。
  只提示不拦截 —— 现场可能就是有意存本机，不该把人挡住。

- **团体总分** → `CalculateTeamScores()` 从 `_swimmers` **现算**，填 `_teamScores`，不落地。
  本机确认成绩时由 `ScoringConfigCore` / `CalcTeamScore_Click` 触发重算。
  **但计时端回推那条路原来谁都不触发** —— 主服务器上的团体总分会一直停在旧值。
  已在 `HandleHeatConfirmedPush` 里补上重算。

### 这个项目的失败模式（重要）

到目前为止查出的问题，**没有一个是会报错的**：

- 四个 exe 一直是 32 位 → SQLite 原生库对不上 → 库打不开，失败被 catch 吞掉
- 「比赛日程」用本地 socket 数判断有没有大屏 → 计时端恒为 0，必然误报
- 确认成绩不更新主服务器内存 → 数据在库里好好的，界面上什么都看不见
- 团体总分在回推路径上不重算 → 一直停在旧值
- 上面那四层

**所以验收一律用客观判据，不看界面**：查库、数 TCP 连接、抓 WebSocket 报文、
验二进制里的字符串、读 log 文件。凡是"看起来正常"的结论都不作数。
