## ① 计时端「比赛控制」页功能齐不齐 —— 齐

计时端只保留「比赛控制」一个标签页（`MainWindow.xaml.cs:482` 的 `keep` 集合，
其余标签页是 `Visibility.Collapsed` **不是移除** —— 所以 UIA 里仍能看到 9 个，
调试时别被这个迷惑）。

该页内容跟主服务器**完全相同**（两个 exe 共用同一份 `MainWindow.xaml`）：

| 区块 | 内容 |
|---|---|
| 赛程导航 | 场次/项目/组次树、上一组、下一组 |
| 比赛控制 | 计时复位、准备就绪、M.发令、停表、确认本组成绩、打印成绩、公布项目总排名 |
| 泳道操作 | DNS/DNF/DSQ/TRI、取消备注、盲表成绩、道次开关、全部开关、手动输入、手工补段 |
| 显示控制 | 出发表、比赛视图、组成绩、总排名、团体、颁奖、裁判介绍、欢迎、成绩发布、比赛日程、图片/视频、PPT、大屏样式、记录显示、显反应时 |
| 系统硬件 | 网络连接、设备测试、参数设置 |

**结论：界面上不缺东西，不需要新做界面。**

⚠️ 但「显示控制」这一组里的功能，**只有「比赛日程」被完整验证过**（2026-08-28 修了它
误报"没有已连接的大屏"的 bug）。其余 11 个按钮我只做了**代码审查**（都走
`BroadcastDisplayMode` / `BroadcastJsonToClients`，那两条有 RTC 转发分支），
**没有在计时端上逐个点过**。转移前应该逐个实测一遍。

## ② meet.db 依赖 —— 通道已通，但计时端没配

### 现在的分工（`Db/MeetDbBridge.cs`，已实现）

| 操作 | 走哪 | 说明 |
|---|---|---|
| `UpdateLane` / `UpdateSplit` / `SetRaceState` | **本机** `current_heat.db` | 比赛中每一次触板都写这里，不过网 |
| `GetSchedule` / `OpenHeat`（取名单） | 远端 `MEET_RPC` | 只在**选组**时调一次 |
| `CommitHeat`（确认成绩） | 远端 `CommitHeatFrom(_local.GetLiveHeat())` | 把本机成绩**整组带过去**再入库 |
| 破纪录 | 随 `CommitHeat` 返回 `RecordBreak` 列表 | 服务端判定，不用单独接 |
| 团体总分 | `CalculateTeamScores()`（`:12781`） | 目前在**主服务器**算 |

`RemoteMeetService` 对"当前组库"类操作直接抛异常（`:157 NotOverWire`），
从设计上就堵死了"比赛中过网写数据"这条错路 —— 这是对的，别去改它。

**这条链路 2026-08-27 实测过：比赛中 `GetSchedule` 可用，返回 45 行带 RoundId。**

### ❌ 缺口：计时端根本没进远端模式

`MeetDbBridge` 自己读配置（`:70-99`）：

```
命令行   --meet-server 192.168.1.10[:3002]
配置文件 <程序目录>\meet_service.json  { "Host": "..." }
```

**但安装包的 `RemoteTimingControl\` 目录里没有 `meet_service.json`**
（只有 `RemoteTimingServer.txt`，那是另一回事）。

后果：计时端会**退回本地模式**，自己开一个 `meet.db`。比赛中不会立刻出错
（当前组走本机库），但**确认成绩会写进计时端自己的库**，主服务器那边什么都没有。
这是转移方案里**最危险的一个洞**，必须先堵。

**要做的**：安装时在计时端目录写 `meet_service.json`，Host 指向主服务器；
或者在计时端界面上把已有的「主服务器 IP」输入框跟它打通（现在那个框只管
EditorSync，不管 MeetDbBridge，**两套配置各走各的**——这本身也该合并）。

### 还需要逐个确认的（我没查）

- **打印成绩**：走本机打印机还是主服务器？计时端旁边有没有小票机？
- **公布项目总排名（存盘）**：存到哪台机器的盘？
- **团体总分**：现在在主服务器算。主服务器不再做比赛控制之后，谁触发重算？

## ③ 掉线接管 —— 现在没有，建议这样定

**现状**：主服务器的「比赛控制」页可以用 `--role server` 移除
（`ApplyMachineRoleToUi()` → `tc.Items.Remove(RaceControlTab)`，`:404`），
计时命令也会被拒并回执 `TIMING_CMD_REJECTED`。**但这个开关目前没人用**，
现场跑的是 `standalone`。

**问题**：一旦主服务器真的把比赛控制去掉，计时端死机 / 网线断了，就没有第二条路。

**建议：不做自动接管，做"手工降级"。**

理由：自动接管要处理"两台都在控制"的脑裂，比赛现场出这个问题比停几分钟更糟。

具体做法：

1. 主服务器**保留**比赛控制页的代码和界面，用 `--role server` **默认隐藏**
2. 加一个隐蔽的「应急接管」入口（比如设置页里，需要二次确认）
3. 接管时先检查计时端是否真的离线（主服务器知道 RTC 有没有连着）
4. 接管后在界面上挂持续可见的警示条，提醒赛后要恢复

这样**代码一行不用删**，跟你定的"不删代码、只用运行时开关"是一致的。

## 建议的实施顺序

| 步 | 做什么 | 风险 |
|---|---|---|
| 1 | 计时端配 `meet_service.json`，与「主服务器 IP」输入框打通 | 低，纯配置 |
| 2 | 计时端上**逐个实测**显示控制那 11 个按钮 | 低，只是测 |
| 3 | 查清打印/存盘/团体总分三项落在哪台机器 | 低 |
| 4 | 完整跑一场：计时端控制 + 主服务器只做数据 | 中，要真跑 |
| 5 | 主服务器切 `--role server`，验证比赛控制页确实进不去 | 低，开关已有 |
| 6 | 加「应急接管」入口 | 中 |

**第 1 步不做完，后面都别做** —— 成绩会写进计时端自己的库，赛后才发现就晚了。
